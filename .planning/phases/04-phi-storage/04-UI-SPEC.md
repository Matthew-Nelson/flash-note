# Phase 4 — UI Design Contract

> Visual and interaction contract for Phase 4 (PHI Storage). Extends the mature FlashNote design system shipped in UI Overhaul Phases A-E. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope:** Patient list/detail/new, notes list/detail/new, patient typeahead, version history, per-section inline editing, optimistic lock conflict UX, style preferences in settings, archive confirmation, PHI cleanup on navigation, print header update.

**Non-negotiable:** HIPAA Engineering Rules 11-14 (CLAUDE.md) — aria-label on icon buttons, WCAG AA 4.5:1 contrast, aria-live for dynamic content, semantic landmarks + single h1 + sequential headings.

## Typography

FlashNote runs an 11-step scale; Phase 4 surfaces use a **subset of exactly 4 sizes + exactly 2 weights** to maintain hierarchy. Body line-height is `leading-relaxed` (1.625) for note content, `leading-normal` (1.5) for UI chrome. Heading line-height is `leading-tight` (1.25).

| Role | Size | Tailwind | Weight | Line height | Phase 4 usage |
|------|------|----------|--------|-------------|---------------|
| Page title (h1) | 24px | `text-fn-2xl` (`--fn-text-2xl`) | 600 semibold | `leading-tight` (1.25) | Patient name, note title (auto-generated), page heading (`/dashboard/patients`, `/dashboard/notes`) |
| Section heading (h2, h3) | 18px | `text-fn-lg` (`--fn-text-lg`) | 600 semibold | `leading-tight` (1.25) | Card titles ("Patient Info", "Context", "Notes"), SOAP section headers, "Edit History" disclosure button |
| Body / table cell / label | 14px | `text-fn-base` (`--fn-text-base`, default) | 400 normal (content), 600 semibold (form labels + table column headers) | `leading-normal` (1.5) for UI, `leading-relaxed` (1.625) for note-section content | Patient rows, note previews, form inputs, form labels, buttons, error/helper text |
| Micro / meta (timestamps, badges, column headers) | 12px | `text-fn-xs` (`--fn-text-xs`) | 400 normal (timestamps, counters, metadata), 600 semibold (source badges + table column headers, uppercase `tracking-fn-wider`) | `leading-normal` (1.5) | Timestamps, "3 edits" disclosure counter, metadata row (date · duration · modality), table helper text, source badges on version history (`GENERATED` / `MANUAL EDIT`), table column headers when space-constrained |

**Rules:**
- Exactly one `<h1>` per page (Engineering Rule 14). Heading nesting sequential — h1 (page title) → h2 (major card) → h3 (subsection if needed). No `h4+` in Phase 4.
- Weights: exactly two — `400` (normal) and `600` (semibold). No 300, 500, 700, or 800. Phase 4 form labels use **600 semibold** (consistent with `Button.tsx` and `Card.tsx` headings). If the existing `/dashboard/settings` page uses 500 for legacy form labels, do NOT promote that pattern into Phase 4 surfaces — the planner may raise a small follow-up to reconcile legacy Settings labels if visible inconsistency surfaces.
- Sizes: exactly four — 24px, 18px, 14px, 12px. The 13px `text-fn-sm` token is NOT used in Phase 4; meta/timestamp/badge content collapses to 12px `text-fn-xs`.
- Letter spacing: `tracking-fn-tight` (-0.02em) on h1 only. `tracking-fn-wider` (0.08em) on uppercase micro-labels (source badges, sidebar section headers). Default (-0.01em) everywhere else.
- Tabular numerals for timestamps and version numbers: use `font-variant-numeric: tabular-nums` via `className="tabular-nums"` to stop version counters jittering in disclosure buttons.

### Destructive confirmations (Archive)

**Pattern: Modal `ConfirmDialog` component.** New shared component `web/src/components/ui/ConfirmDialog.tsx`. Rationale: two-step inline buttons invite misclicks; toast-with-undo is the wrong model for HIPAA audit events (the audit log fires on first click, so undo is illusory). A focused modal with explicit destructive CTA is the safest UX for a clinical environment.

Requirements:
- Rendered as `role="dialog"` with `aria-modal="true"` and `aria-labelledby` pointing at the modal heading.
- Focus trap: initial focus on the destructive button is NOT acceptable — initial focus MUST go to the Cancel button (safer default). Tab cycles within modal, Escape closes.
- Backdrop click closes (equivalent to Cancel). Prevent body scroll while open.
- Destructive button uses a new `Button variant="destructive"` (add to `Button.tsx` — bg `--fn-error`, hover `--fn-error-dark`, white text, min 44px, same focus-ring rules).
- Do NOT auto-close after confirm — let the parent action complete and redirect/update state, then unmount the modal.
- aria-live region inside the modal announces loading state ("Archiving patient...") and errors.

**Copy matrix:**

| Action | Modal heading | Modal body | Destructive CTA | Cancel CTA |
|--------|---------------|------------|-----------------|------------|
| Archive patient | Archive {firstName} {lastName}? | This patient will be hidden from your active patient list. Their existing notes remain accessible. You can restore this patient later by contacting support. | Archive patient | Keep patient |
| Archive note | Archive this note? | This note will be hidden from your notes list. Version history is preserved. You can restore it later by contacting support. | Archive note | Keep note |

**Why "Keep" not "Cancel":** explicit positive framing — the user sees exactly what each button does. Industry-standard pattern; less ambiguous than Cancel/Yes.

**What "archive" means to the user (in body copy):** "Hidden from your list" — do NOT say "deleted" (rows remain in DB with `archived_at`). Do NOT say "permanently" — archived records are restorable via support in principle.

## Interaction Contract (locked from "Claude's Discretion")

This section converts every discretionary UX item from CONTEXT.md into a locked decision. Executor MUST follow.

### Patient typeahead debounce

- **Debounce:** **250 ms** on the `onChange` of the input. Short enough to feel responsive, long enough to avoid thrashing the Server Action + DB under sustained typing.
- **Min query length:** 2 characters before firing the search. Below 2, show "Start typing to search" helper text (no request fired).
- **Max results rendered:** 10 options in the listbox at once. If server returns more, show "Showing first 10 — refine your search to see more." as a disabled last row (not an `<option>`, styled as helper text inside the listbox container).
- **Request cancellation:** Each keystroke aborts the in-flight `AbortController` before firing the next request. Prevents out-of-order renders.
- **Keyboard contract (WAI-ARIA 1.2 combobox, confirmed in RESEARCH §9):** ArrowDown opens listbox + focuses first option, ArrowUp from input wraps to last option, Enter selects active option, Escape clears listbox (retains input text), Tab exits combobox and commits nothing, Home/End jump to first/last option.
- **Selection UX:** On select, collapse listbox, replace input value with `{firstName} {lastName}`, render a small "Clear" (X) icon-button on the right to un-select. Form submit is blocked until a patient is selected.

### Version history UI

- **Locked shape: inline disclosure per section.** Below each `<EditableNoteSection>` render a `<button aria-expanded={expanded} aria-controls={bodyId}>History (N edits)</button>` that toggles a `<div id={bodyId} hidden={!expanded}>` containing the version list. Matches RESEARCH §8.3a recommendation.
- Hide the disclosure button entirely when `versionCount === 1` (no history to show).
- **Version list ordering:** DESC by `version` number (newest first). Current version appears first and is labeled "Version {N} (current)".
- **Per-version block:** heading row (Version N + source badge + relative timestamp) over a collapsible content block containing the full section content as a read-only pre-wrapped text block. Each version block also collapses independently (second-level disclosure). This keeps page length manageable for heavily-edited notes.
- **Diff:** Not in Phase 4. Shows full text. (Marked nice-to-have in RESEARCH §8.3a — deferred unless surplus time.)
- **Audit event:** `NOTE_HISTORY_VIEWED` fires on note-detail page load (eager-load decision per RESEARCH §8.3a), not on disclosure click. This matches "loaded the history view" semantics and keeps the audit one-per-visit. Document the rationale inline per D-08.

### Archive confirmation flow

- **Locked shape: modal `ConfirmDialog`** (see Copywriting > Destructive confirmations for full spec).
- **Not** inline confirm (too easy to misclick). **Not** two-step button (ambiguous affordance). **Not** toast-with-undo (audit fires on first confirm — undo would require compensating row which we do not build).
- Initial focus on Cancel ("Keep patient" / "Keep note"), NOT on the destructive button.

### Section edit save/cancel flow

- **Locked shape: explicit save with inline Save/Discard buttons.** Entering edit mode replaces the read-only content with a `<textarea>` (auto-sized via `field-sizing: content` with fallback to manual row calculation) and shows `[Discard changes] [Save section]` buttons in a flex row below.
- **Not** auto-save on blur (auto-save in a clinical amendment trail creates noise versions from accidental tab-aways). Explicit commit is the professional model.
- **Dirty state:** If the user attempts to navigate away while ANY section is in edit mode with unsaved changes, fire a `beforeunload` confirm + an in-app Next.js `beforeunload`-style prompt. Copy: "Leave this page? Your unsaved section edits will be lost." (implementation detail: track per-section `isDirty` in a `Map<sectionId, boolean>` owned by the notes detail page — see Loading/State section below).
- **Undo within edit mode:** "Discard changes" reverts to the last-saved content immediately without a confirmation (lossy, but the user explicitly chose discard).
- **Save error:** If the action returns a non-conflict error, keep edit mode open, show the error alert above the textarea with the curated string, and keep the textarea's current value (don't revert on error — user's changes are preserved so they can retry).
- **Save success:** Collapse back to read-only mode, fire the "Section saved." aria-live announcement, refresh version count on the disclosure button.

### Optimistic lock conflict UX (409)

- **Locked shape: blocking inline alert above the conflicting section** (not a modal). Rationale: a full-page modal disrupts the mental model ("which section was changed elsewhere?"). An inline assertive alert anchored to the note lets the user read their own pending changes before refreshing.
- **Component:** `<Alert variant="error" role="alert" aria-live="assertive">` with embedded `<Button variant="secondary">Refresh to see latest</Button>`. Alert also contains a secondary text link "Copy my changes" that puts the user's in-progress textarea text on the clipboard so they can paste after refresh (defensive — protects their work).
- **When to show:** Only when `updateNoteSectionsAction` returns `error: 'conflict'` (either optimistic-lock failure OR `(note_id, section_id, version)` UNIQUE violation — both surface as the same code per Risk #2 in RESEARCH.md).
- **Dismissal:** The alert is dismissible via `onDismiss` but clicking Refresh is the recommended path. The alert announces via `aria-live="assertive"`.

### Loading state composition

- **Server Components stream wherever possible.** Each page uses Next.js `<Suspense boundary>` with a skeleton fallback to avoid blocking on the slowest DAL query.
- **Skeleton shapes (content-shaped, NO spinners — per UI Overhaul Phase E decision):**

| Page | Skeleton shape |
|------|---------------|
| `/dashboard/patients` | Header (static) + table with 5 ghost rows, each row has 3-4 grey bars matching column widths. Shimmer animation `animate-fn-shimmer` (already in preset). |

- **Spinners:** Only in buttons during in-flight actions (existing `Button` has `loading` prop — reuse). Do NOT use full-page spinners. The existing `Spinner` is reused for in-button loading state; nothing else.
- **Typeahead in-progress:** Show a small muted "Searching..." text below the input (not a spinner). Announce via aria-live.

### PHI cleanup on navigation (Rule 4)

- `usePhiCleanup` hook (spec in RESEARCH §8.6) wired into every page that renders PHI: patient detail, notes detail, notes/new (after submission), generator form.
- Cleanup function clears:
  - Generated/saved note content state.
  - Per-section `editBuffer` map.
  - Patient context textarea value.
  - Typeahead query string and selected-patient state.
  - Clipboard clearing: ONLY when the session wrote to it (tracked via `clipboardWrittenRef`).
  - In-flight requests aborted via `AbortController.abort()`.
- Navigation dirty-state prompt runs BEFORE cleanup (so user can cancel). If they proceed, cleanup runs.

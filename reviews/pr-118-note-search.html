web/src/app/dashboard/notes/page.tsx:41 · raised by claude-A, claude-B, gemini (claimed High) · Medium

sp.q?.trim() assumes a string, but a repeated query parameter resolves to string[]. /dashboard/notes?q=a&q=b throws TypeError: sp.q.trim is not a function and drops the route into the error boundary.

Verifier: Confirmed against the installed Next.js 16.3.1 in the worktree: SearchParams = { [key: string]: string | string[] | undefined }, and searchParamsToUrlQuery explicitly pushes repeat occurrences into an array. Re-rated from the third leg's High to Medium: trivially reachable via a hand-typed or shared link, but single route, single request, no persisted state.

web/src/server/dal/clinical-notes.ts:228 · raised by claude-A, claude-B, gemini · Medium

cn.content::text ILIKE searches the JSONB serialization, not the note prose — so the literal keys (sectionId, title, content) and the section titles are inside the searched text. A therapist searching plan, assessment, objective, subjective, title or content matches every note in scope.

Verifier: The verifier reproduced this against a real Postgres 17 instance: on a row with all four sections, content::text renders as [{"title": "Subjective", "content": "...", "sectionId": "..."}, ...] and all six terms evaluate true. This is not an edge case — the built-in SOAP template seeded at 002_phi_storage.sql:242-266 is the only template the app can currently produce (there is no create path in note-templates.ts), and its titles are literally Subjective/Objective/Assessment/Plan. So those are the section names of 100% of notes. The DAL docstring at lines 195-197 ("matches either the therapist's shorthand or the generated SOAP sections") overstates the precision actually delivered.
